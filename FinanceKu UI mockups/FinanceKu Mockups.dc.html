briefAssumptions, context & what I changed

Context I pulled from your code

  • Tokens from index.css: brand #00ad6c / orange #eb6834, card radius 22, shadow 0 4px 20px rgba(0,0,0,.05), the 8-step single-hue chart ramps, semantic green/red/amber tints.
  • Routes today: /chat (default), /spending, /investments, /settings. Three floating capsules on desktop, bottom bar + horizontal section tabs on mobile.
  • Spending page renders 8 sibling chart cards of equal weight; mobile swaps them into a swipeable carousel.
  • Everything is set in Source Serif 4 — including tabular figures and 11px labels.

Why it feels clunky (my read)

  • No answer layer. Cards are titled by chart type ("Savings Rate Over Time (%)"), so the user has to do the interpreting. Eight equal cards = no hierarchy.
  • Two competing navigations on mobile (bottom bar + scrolling section tabs) and a third state (filter popover) that hides the period.
  • No landing surface. /chat is the default route, so the app opens on an empty box instead of "where do I stand".
  • The pastel gradient page competes with white cards at every edge; large-radius cards on a busy field read soft/unfocused.
  • Serif for data. Source Serif is lovely for headlines, muddy at 11px and in dense numeric tables.

The seven moves in these mockups

  1. An Overview home — net worth, month-to-date, next commitments, one Finn prompt.
  2. Insight-first cards — plain-language headline, chart as evidence beneath.
  3. One persistent period control replacing the filter popover.
  4. Progressive disclosure — 3 primary charts, the rest behind "More insights".
  5. Sidebar rail on desktop, 4-tab bar + Finn as a floating pill on mobile.
  6. Calm canvas, brand gradient reserved for the one hero block.
  7. Type pairing — Source Serif 4 for headings & figures, IBM Plex Sans for UI, tabular everywhere.

Assumptions

  • SGD, ~S$2.5k/mo spend, invented but plausible data.
  • Mobile = iPhone 402×874. Desktop = 1280 wide.
  • Green is primary; orange shown alongside on the two dashboards.
  • lucide icons drawn as simple stand-ins — swap in the real set in code.

richRich replies — getting charts and suggestion chips out of a text-only agent

The principle: the agent keeps returning text, and additionally returns structure. text is always populated and is always the truth; blocks and actions are optional evidence and shortcuts. Telegram renders text + buttons, the web renders all three, and a renderer that meets an unknown block type falls back to the text. That way one agent serves both channels and nothing breaks when you add a block type. answer_question(..., channel=) already exists — keep it for rendering decisions only, never for two different answers.

1 · The envelope

One shape, returned by answer_question instead of str. Add it to backend/schemas.py as the shared contract.

AgentReply {
  reply_id: str
  text:    str                 # always set — Telegram & a11y fallback
  blocks:  [Block]             # optional evidence
  actions: [Action]            # optional next steps
}

Block =
  | {type:"metric",     label, value, delta, delta_dir}
  | {type:"comparison", series:[{label, value}], unit}
  | {type:"breakdown",  rows:[{label, value, pct, color_key}]}
  | {type:"timeseries", points:[{t, value}], compare_points?}
  | {type:"txn_list",   transaction_ids:[...]}
  | {type:"receipt_draft", draft_id, lines:[{description,
      amount, category, confidence}]}

Action {
  id, label, style:"primary"|"secondary"
  effect: {endpoint, method, payload} | {navigate: "/spending?cat=food"}
  confirm: bool
}

Why effect is server-described: the “Cap Food & Drink at S$650” chip in 1e is just POST /api/budgets {category:"Food & Drink", monthly_limit:650}. Ship the call with the reply and neither client needs to know how budgets work.

2 · Where the structure comes from

Don’t ask the model to draw JSON charts from memory — it will invent numbers that disagree with the prose. Two safer routes, use both:

a. Capture tool results (no extra model call)
The agent’s tools in bot/finance_agent.py already return real aggregates. Wrap the tool dispatcher so every call appends {tool, args, result} to a per-turn evidence buffer, and map known tools to block types (get_spending_summary → breakdown). Deterministic, free, always matches the text.
b. A final present(…) tool
Give the model one more tool that takes {show:[evidence_ids], actions:[…]} — it chooses which evidence to surface and what to offer next, but never restates the figures. If it doesn’t call present, you get today’s plain text. That’s the graceful default.
